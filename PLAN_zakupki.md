# Детальный план реализации: надёжный сбор закупок для Энергореестра РФ

Дата: 20.11.2026 · Версия проекта: 2.1 · Статус: **реализовано и проверено локально; публикация — только после согласования**

> Фактическая реализация (2.1). Дальше по тексту — исходный план и результаты разведки.
> Отличия: добавлены GenTender + прямые адаптеры ТЭК-Торг / ЭТП ГПБ / Росэлторг,
> дедупликация одного тендера из разных источников, составные ключевые фразы
> `{label, search, must}` (опорное слово в API, полная фраза — локально),
> бюджет запросов `requestBudget` и новая схема записи. ГосПлан ищет только по словам
> (обход по ИНН перенесён в GenTender, чтобы не получать 429). Актуальное состояние — в `AGENTS.md`.

## 1. Цель и требования

Собрать «надёжную машину» мониторинга закупок, которая:

1. **Не пропускает информацию** — несколько независимых источников с взаимным резервированием (failover), а не один парсер сайта.
2. Привязывает каждую закупку **только к организациям реестра (339 записей)** — совпадение по ИНН или названию, станции → родительское юрлицо.
3. Ищет по ключевым словам (`турбины`, `уплотнений`, `лопаток`) и по предприятию/филиалу (включая автодополнение в UI).
4. Разделяет **действующие** закупки и **завершённые** с настраиваемой глубиной по дате.
5. Работает **бесплатно** (или с бесплатным стартом) и запускается **раз в сутки в 06:00 по Москве** (03:00 UTC).
6. Ведёт **подробный лог**: что, откуда, когда, сколько записей, успех/ошибка. Ссылка на лог — внизу страницы.
7. Ломает минимальное количество существующего кода:asic реестр, карта, печатная версия не меняются.

## 3. Архитектура «машины»

```
scripts/collect-tenders.js     orchestrator:QUEUES → ADAPTERS → NORMALIZE → DEDUP → MATCH → WRITE → LOG
├── scripts/sources/gosplan.js      (primary, REST JSON, 44/223/615)
├── scripts/sources/eis-html.js     (fallback, текущий HTML-парсер)
├── scripts/sources/ftp-xml.js      (ЗАПЛАНИРОВАНО, не реализовано)
├── scripts/sources/krasoft.js      (ЗАПЛАНИРОВАНО, не реализовано)
├── scripts/lib/normalize.js       единая схема записи
├── scripts/lib/match-org.js       сопоставление с 339 организациями
├── scripts/lib/throttle.js        rate-limit + retry + circuit breaker
└── scripts/lib/logger.js           структурированный лог источников

data/tenders.json                выдача ( подаётся в UI)
data/tenders-status.json         статус последнего прогона
data/collect-log.json            подробный лог (кто/что/когда/успех)
log.html + js/log.js             страница просмотра лога
js/tenders-data.js               АВТО: window.TENDER_DATA (добавить log)
```

### 3.1 Единая схема записи

```js
{
  id, title, customer, customerInn, matchedOrgId, matchedOrgName,
  etp: 'EIS'|'BIDZAAR'|..., source: 'ГосПлан API'|'ЕИС HTML'|...,
  price, published, deadline, updated, stage, phase: 'active'|'archive',
  url, keywords: [], enterpriseIds: [], foundAt, lastSeen
}
```

### 3.2 Приоритет и failover

1. **ГосПлан API** — запросы по ИНН всех организаций реестра + по ключевым словам; `stage=1` (действующие) и `stage=3/4` + `published_forpast` (архив).
2. **Текущий HTML-парсер НЕ удаляется** — он переносится в `eis-html.js` как резервный источник и дорабатывается отдельно. По умолчанию работает API. При 429/5xx/таймауте → `throttle.js` делает backoff (6→35→70 с), затем **circuit breaker** и переход к `eis-html.js`.
3. Если и HTML недоступен →成功率 `krasoft` (если настроен ключ), затем **сохранение предыдущих данных** без очистки.
4. Каждый переход фиксируется в логе с причиной.

### 3.3 Надёжный охват (главное требование)

- ИНН **всех** организаций с инн из реестра (≈81 юрлицо) + названия станций как алиасы → поиск по `customer=<ИНН>` и `object_info=<название>`.
- Ключевые слова × режимы: `active` и `archive` с `published_forpast=30d`.
- Постранично `limit=100` + `skip`, пока страница не пустая или не достигнут `maxPages`.
- Дедупликация по `purchase_number`, объединение `keywords`/`enterpriseIds`.
- Сверка с реестром обязательна: чужые заказчики отсекаются.
- **Никогда не очищать** `tenders.json` при частичном провале; писать `partial: true` в статус.

## 6. Риски и меры

| Риск | Мера |
|---|---|
| ГосПлан test-сервер нестабилен / 429 | throttle 6.5 с, backoff, circuit breaker, переход на HTML/FTP, продакшн-ключ по событию |
| Источники меняют вёрстку/условия | адаптеры изолированы, тесты-фикстуры, версия источника в логе |
| Слишком много запросов по 339 организациям | сначала ИНН юрлиц (81), затем дозапросы только по тем, где есть результаты; кэш skipped |
| Коммерческие закупки вне ЕИС | Bidzaar/Krasoft как отдельный адаптер; глубокие ссылки в UI |
| Лог вырастет | хранить последние N run (например 30), ротация |
| Случайно сломать работающий реестр | все новые файлы изолированы, минимальные правки в `app.js`/`index.html`, полный локальный прогон |
